Day 7 - VLSM & Static Routing - [02/09/2026]
Built: Subnetted 192.168.5.0/24 using VLSM to support 4 LANs with different host requirements (45, 64, 14, and 9 hosts)
Configured: Assigned the first usable address in each LAN to the PC, and the last usable address to the router's interface
Configured: Static routes on R1 and R2 so each router could reach networks it does not directly own
Tested: Verified show ip route output showed connected (C) routes for locally owned LANs and static (S) routes for remote LANs
Tested: Pinged between PCs across different LANs - first two pings timed out, then succeeded
Learned: Initial ping timeouts were caused by ARP resolving the destination MAC address for the first time, not a misconfiguration - this is normal ARP behavior
Learned: In VLSM, subnets must be allocated largest requirement first to avoid overlapping address ranges within the same parent network
Issues: None

Day 8 - Inter-VLAN Routing (Multiple Physical Interfaces) - [02/09/2026]
Built: 3 VLANs (Engineering, HR, Sales) on SW1, each in a separate /26 subnet, with 3 separate physical connections from R1 to SW1
Configured: Assigned static IP addresses to each PC, using the last usable address in each subnet as the default gateway
Configured: One R1 interface per VLAN, each set to the gateway address configured on the PCs
Configured: Assigned SW1's interfaces to the correct VLANs, keeping the R1-facing interfaces correctly matched to each VLAN
Configured: Named the VLANs (Engineering, HR, Sales)
Tested: Verified ping connectivity between PCs across different VLANs, confirming inter-VLAN routing worked
Tested: Sent a broadcast ping to each subnet's broadcast address in Simulation Mode to observe which PCs received it
Learned: A broadcast ping only reaches devices within the same VLAN/subnet - it does not cross VLAN boundaries, confirming VLANs correctly isolate broadcast domains
Issues: None



Day 9 - VLAN Trunking & Router-on-a-Stick - [11/09/2026]
Built: 3 VLANs (10, 20, 30) across two switches (SW1, SW2) and one router (R1), each VLAN in its own /26 subnet
Configured: Access ports on SW1 and SW2 connecting to PCs, assigned to the correct VLANs
Configured: Trunk link between SW1 and SW2, allowing only the necessary VLANs and setting an unused VLAN as the native VLAN
Configured: Router-on-a-stick between SW2 and R1 - created subinterfaces on R1 for each VLAN, with 802.1Q encapsulation matching each VLAN
Configured: Assigned the last usable address of each subnet to R1's subinterfaces
Tested: Verified ping connectivity between PCs across all VLANs and switches
Learned: A trunk's native VLAN carries untagged traffic - using an unused VLAN as native avoids accidentally mixing native VLAN traffic with a real data VLAN (a known security consideration)
Learned: Router-on-a-stick uses one physical link with multiple logical subinterfaces, unlike Day 8's method which used a separate physical interface per VLAN
Issues: None

Day 10 - Floating Static Routes - [22/09/2026]
Built: Dual-ISP topology with Enterprise A (R1, R2) connecting to two ISPs (SPR1 via ISP A cloud, SPR2 directly) for redundant internet access
Configured: A primary default static route on R1 and R2 pointing toward one ISP path
Configured: A floating static route as backup, using a higher administrative distance so it only activates if the primary route fails
Tested: Verified show ip route output - primary route (S*) shown as active with the lower AD, floating route hidden from the table while the primary is up
Tested: Pinged across the topology - some initial timeouts observed, consistent with route convergence/failover behavior
Learned: A floating static route only appears in the routing table and gets used once the primary route (with lower AD) becomes unavailable - this provides automatic backup path failover without needing a dynamic routing protocol
Issues: None

Day 11 - OSPF (Single Area) - [28/09/2026]
Built: 4-router single-area OSPF network (R1-R4, all in Area 0), connected via multiple FastEthernet links plus a switch and PC for end-to-end testing
Configured: OSPF process on each router, advertising the correct networks into Area 0
Tested: Verified show ip ospf neighbor and adjacency states - confirmed neighbors reached FULL state (not stuck in INIT/2-WAY/EXSTART/LOADING)
Tested: Verified show ip ospf interface brief - confirmed correct Process ID, Area, cost, and DR/BDR state per interface
Learned: On multi-access networks, OSPF elects a DR (Designated Router) and BDR (Backup DR) to reduce the number of adjacencies formed - R3 showed as DR with a neighbor elected BDR, rather than every router forming full adjacencies with every other router
Learned: The %OSPF-5-ADJCHG log message confirms neighbor state transitions (e.g. LOADING to FULL), useful for verifying adjacency formation during troubleshooting
Issues: None
